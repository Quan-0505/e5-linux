# TCL T512N：低刷新率与条纹对照

## 原厂与实机依据

本机为 TCL T512N / PB8，原厂
`TCL/PB8_100A_FIH/PB8:13/TP1A.220624.014/512NCA05:userdebug/release-keys`，
原厂内核 `5.15.119-android13-8-g10da4d9c53de-ab1`。

本机 DT 面板 `lcd_ili9488_easyquick_mipi_fhd` 要求 320×480、16 MHz，
水平总长 500、垂直总长 534，名义刷新率为 59.925 Hz；单通道 RGB888，
DSI 速率配置为 427 Mbps。这些配置和原厂 `sprd-drm.ko` 的时钟选择路径均已核对。
原厂模块 SHA256 见 `dumps/t512n-stock-20261018/reference/manifest.json`。

不能把面板 sysfs 显示的 16 MHz / 59.92 Hz 当作实际频率：它们由模式参数
计算而来。2026-10-18 保存的 Android 实测、以及本次修改前的 OpenWrt 都是：

| 时钟 | 修改前 |
| --- | --- |
| PIXELPLL | 264576000 Hz |
| PIXELPLL/16 | 16536000 Hz |
| dispc0-dpi | 8268000 Hz |

旧 Android 也有同样闪烁、约 30 Hz 的用户反馈，因此不是已证明的 OpenWrt
新增缺陷；目标模式与实际时钟链的差异则已确认。

## 修复范围

只在 `devices/t512n/prepare-kernel.py` 接入 `display-clock.py`，并再次检查
活动面板名称、16 MHz 模式和 /16 分频。其他机型不调用此适配器；同一内核中
不同面板或不同模式也不进入这条分支。

本机 DPI 是 /1..8 的三位整数分频器，显示复合时钟不会向 PLL 传递设频请求。
先把 PIXELPLL 配置为 2.048 GHz，再由 /16 和 /8 得到 16 MHz。该 VCO 位于
UMS9621 对应显示时钟实现注明的 1.6–3.2 GHz 范围内。
PLL 设置失败向调用者返回错误，不伪装成功。

没有改面板初始化命令、伽马、正负电压、RGB 格式、DSI 速率、分辨率、porch，
也没有添加启动服务、轮询或每次亮屏的用户态重置。

## 验证结果与限制

- 先用匹配当前内核/BTF 的临时模块对照；用户确认“条纹减少，明显更流畅”。
- 使用已登记的 T512N 源码视图/对象目录构建完整内核和配套模块，通过既有
  构建检查。生成的实际 C 分支通过作用范围、幂等、异常源布局和设频失败回归。
- 部署完整配套后重启，未加载临时诊断模块，PIXELPLL=2048000000、
  DPI=16000000 Hz，显示连接及屏幕状态同步正常，模块哈希与构建输出一致。
- 通过 DRM vblank 时间戳测量：重启后 60 个帧同步约用 1.033492 秒，即
  **58.06 Hz**。这是实测结果，不写成精确 60 Hz；名义模式仍为 59.925 Hz。
- 未见新增 underflow/underrun、模块 BTF/符号错误。永久版重启后的视觉效果和
  长时间使用仍需用户观察，不能保证残余条纹/偶发缺色已经完全消除。
- 手动面板重新初始化并未消除条纹，故没有把重复初始化作为永久修复。

本次读取全局 `clk_summary` 曾触发 `sprd_gate_is_enabled` 总线 SError，设备
自动重启。历史记录已有同类限制，本次查阅不够及时，已保存故障并停止使用
该接口；后续仅读取已核验的目标时钟节点。

## 部署时发现的独立状态

- 旧开发启动镜像的 AVB 偏移与 ramdisk 尾部重叠，正式部署时使用同一台设备的
  已保存原厂 AVB 元数据重建有效布局，并保留当前命令行、槽位角色和诊断区。
  原厂备份与实机 CID 复核匹配；Android 槽完整哈希未变化。
- 隔离 NV 初始化停在原始 `nr_fixnv2_a` 校验失败；对应主副本有效，其他固定
  副本检查通过。仅从本槽有效主副本创建 OpenWrt 的隔离备份工作副本，再交给
  现有准备/配对流程；9 个原始 NV 分区全程只读，操作前后哈希一致。
  没有改公共 NV 策略，也没有把原始坏副本改写成有效副本。

本次证据、备份、临时工具、部署记录在忽略目录
`work/t512n-display-20261022/`。临时工具不进入安装包，不用于其他机型。
